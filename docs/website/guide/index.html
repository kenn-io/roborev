The guide

A review loop you set up once and stop thinking about.

Ten stops from a fresh repo to a team running the same reviewers on every commit and every pull request. Every stop links into the documentation for exact commands and configuration.

  1. Install once, initialize per repo.

    roborev is a single Go binary. roborev init installs a post-commit hook, starts the daemon if it is not running, and registers the repository. It detects hook managers like Husky through core.hooksPath and never edits tracked source.

    Point your coding agent at roborev quickstart and it will inspect the repo and finish the setup, including a machine-readable state for agents that prefer JSON.

    Quick start · Installation

  2. Commit. The review is already running.

    Each commit queues a background review through the daemon's worker pool. The first installed agent in the fallback order picks it up, reads the diff, the commit message, your guidelines, and recent review history, and returns a verdict with findings, severities, and file locations.

    Duplicate hook requests for the same target are coalesced, so several worktrees or editors committing at once still produce one review. Small commits can be batched into one range review with post_commit_batch_size.

    Post-commit reviews · Reviewing code

  3. Read the ledger, not the scrollback.

    Every review lives in a persistent queue with its verdict, findings, the exact prompt, and the agent log. roborev tui shows the queue in the terminal with vim keys and a split-screen layout on wide windows. roborev ui opens the browser workspace served by the same daemon.

    Both read the same SQLite history. A review stays open until you or an agent closes it, so the queue is an honest list of what still needs attention across every repository on the machine.

    Terminal UI · Browser UI

  4. Give the finding back to the agent.

    The fastest path is the one you already use: press y in the TUI to copy a review and paste it into the agent session. From Claude Code or Codex, /roborev-fix pulls every open failing review for the branch, fixes valid findings, documents invalid ones, runs the tests, and closes the reviews.

    With no session open, roborev fix hands the findings to an agent that applies changes and commits. The new commit is reviewed automatically, which closes the loop. Disagree with a finding? Respond on the review and close it with the reason on record.

    Agent skills · Responding to reviews

  5. Let the session fix its own reviews.

    roborev agent-hook install detects Claude Code, Codex, Copilot CLI, Cursor, Factory Droid, Gemini CLI, Hermes, and Qwen and installs their native lifecycle hooks. The daemon counts turns, commits, and failed reviews per session; when a threshold trips, the agent is reminded to run the fix skill for exactly the review IDs that are open.

    Reminders never run roborev fix on their own. One session owns a fix per worktree at a time, hooks fail open when the daemon is unavailable, and roborev snooze silences a worktree while you focus.

    Agent Hook

  6. Refine the branch before anyone else reads it.

    roborev refine finds the oldest failed review on the branch, fixes it in an isolated worktree, commits, waits for the re-review, and repeats. When every per-commit review passes it runs a whole-branch review and loops on that too, until green or --max-iterations.

    The same loop runs as /roborev-refine inside the agent session. Either way, what reaches the pull request has already been reviewed and repaired several times, by agents, while the human reviewer was doing something else.

    Auto-fix with refine

  7. Choose the reviewer per repo and per job.

    A committed .roborev.toml names the agent, model, and reasoning level for each workflow, a backup agent for quota failures, and the review guidelines every reviewer must follow. Global defaults live in ~/.roborev/config.toml; the repo file overrides them field by field.

    The reviewer does not have to be the writer's vendor. A fast model for routine commits, a thorough one for security, a local model behind a proxy for a private codebase: each is one config key.

    Configuration · Supported agents

  8. Add reviewers when the change deserves them.

    A review panel fans one target out to named subagents, each with its own agent, review type, instructions, and timeout, and a synthesis agent merges them into one review. Built-in security, design, and lookahead types swap the rubric; custom types wrap your own Go template in the same schema and verdict.

    For the code you already have, roborev analyze runs duplication, complexity, dead-code, refactoring, API-design, architecture, security, and test-fixture passes, and roborev compact verifies open findings against the current tree before anyone acts on them.

    Review panels · Custom review types · Code analysis

  9. Run the same panel on every pull request.

    Enable the CI poller and the daemon lists open pull requests on GitHub or merge requests on GitLab, runs one panel per PR head against the frozen merge-base range, and posts one synthesized comment. Trusted collaborator discussion is included in the prompt; labels in skip_labels exempt drafts and generated updates.

    Authenticate as a GitHub App so comments and checks come from a bot with repository-scoped permissions, or use your gh login for a personal project. Per-repo .roborev.toml overrides the panel and agents for one project.

    GitHub integration · GitLab integration

  10. Run it as a team, keep it on your machines.

    Every daemon keeps its own SQLite database. Turn on [sync] and each machine pushes and pulls review history through a shared PostgreSQL database, deduplicated by UUID, so the team's reviews converge in one place without any machine depending on the network to review.

    Review event hooks route outcomes to Slack, desktop notifications, or a kata or beads issue tracker. The browser UI's analytics and the JSON exports show what review costs, how long it takes, and what it catches. Configuration experiments let you compare two setups on real branches before you standardize on one.

    PostgreSQL sync · Review event hooks · Analytics
